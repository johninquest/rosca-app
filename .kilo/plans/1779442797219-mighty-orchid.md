# Plan: Show Contribution Details in Delete Confirmation Dialog

## Problem
In `EventDetailPage.jsx:491-498`, the delete-contribution `ConfirmDialog` shows only a generic message — `"This contribution will be permanently removed."` — with no reference to **which** contribution is about to be deleted.

## Root Cause
`deletingContribId` holds only the contribution **id**. The dialog is rendered at line 492 with no derived data passed in, so it can only display a static string.

## Proposed Change (2 files)

### 1. `src/pages/EventDetailPage.jsx`

**Before (lines 490-498):**
```jsx
<ConfirmDialog
  open={!!deletingContribId}
  title="Delete this contribution?"
  message="This contribution will be permanently removed."
  onConfirm={handleDeleteContribution}
  onCancel={() => setDeletingContribId(null)}
  danger
/>
```

**After:**
```jsx
{/* Find the contribution being deleted to show its details */}
{deletingContribId && (() => {
  const contribToDelete = contributions?.find(c => c.id === deletingContribId)
  return (
    <ConfirmDialog
      open
      title="Delete this contribution?"
      message={
        contribToDelete
          ? `${contribToDelete.contributorName} · ${formatAmount(
                contribToDelete.amount,
                event.currency,
              )} (${contribToDelete.date ? formatDate(contribToDelete.date) : '—'})`
          : 'This contribution will be permanently removed.'
      }
      onConfirm={handleDeleteContribution}
      onCancel={() => setDeletingContribId(null)}
      danger
    />
  )
})()}
```

**Key decisions:**
- **Inline IIFE** — keeps `contribToDelete` local to the JSX block, avoiding an extra `useMemo`/`useState`.
- **`contributions?.find(c => c.id === deletingContribId)`** — safe look-up; `?.` handles the brief `undefined` window during loading.
- **Graceful fallback** — if for any reason the contribution isn't found, the old generic message is shown.
- **Reuses existing formatters** — `formatAmount` and `formatDate` are already imported (line 9).
- **`open` is always `true`** — the entire block is only rendered when `deletingContribId` is truthy, so it will unmount itself when the id is cleared. Passing `open` explicitly is more readable than `open={!!deletingContribId}` here.

### 2. `src/components/ConfirmDialog.jsx` — no changes needed

The component already renders a `message` prop as a `<p>` element, fully sufficient for a short inline detail string. No prop or styling changes required.

## UX/UI Rationale

| Principle | How it is addressed |
|---|---|
| **Acknowledge user intent** | The dialog title already asks "Delete **this** contribution?" — showing the specific details completes the mental link between the button the user pressed and what is at stake. |
| **Scannability** | The formatted string (`Name · Amount (Date)`) matches the visual style of every other contribution row on the page (same `font-mono` amount, same date format), so users can mentally map 1:1 without a formatting switch. |
| **Minimal cognitive load** | One line, no separators, no bold/colour. Downside risk is low (the worst case is a slightly long single-line message) and the benefit — preventing a mistaken delete — is high. |
| **Accessibility** | Dimensions stay under the existing `max-w-sm` dialog width, so no reflow or overflow concerns. Screen readers will read the full detail naturally. |
| **Consistency** | Reuses `formatAmount` / `formatDate` already used throughout `EventDetailPage.jsx`, so the text looks identical to how contribution rows present themselves. |

## No Additional Work Required
- No CSS changes — the new text fits comfortably within the existing `max-w-sm` container.
- No tests need to change — the component behaviour and public API of `ConfirmDialog` are unchanged; only `EventDetailPage` passes a richer `message`.
